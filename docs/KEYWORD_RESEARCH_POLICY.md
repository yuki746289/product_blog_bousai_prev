# キーワード調査・記事企画方針

更新日: 2026-09-03

## 1. 目的

新規記事を思いつきだけで増やさず、実際の検索需要・読者の疑問・既存記事との重複を確認した上で、サイトに不足しているテーマだけを追加する。

ラッコキーワード等のキーワード調査ツールは、**記事数を増やすためではなく、検索者の具体的な困りごとを発見するため**に使用する。

## 2. 基本フロー

新規記事候補を作る前に、原則として次の順で確認する。

1. 基点となるテーマを決める
   - 防災リュック
   - 携帯トイレ
   - 台風対策
   - 車の水没
   - 停電
   - 非常食
   - ポータブル電源
   など
2. ラッコキーワード等でサジェスト・関連質問・関連語を取得する
3. 表記違いではなく**検索意図単位**でクラスタリングする
4. 既存記事・Q&A・商品記事との重複を確認する
5. 各クラスタを次のいずれかへ振り分ける
   - 既存記事の追記・強化
   - 新規detail/practical記事
   - Q&A追加
   - 商品記事・商品導線の強化
   - 見送り
6. 新規記事化する場合はpillar/detail構造と内部リンク先を先に決める
7. 公開後はSearch Consoleデータで実際の表示・順位・CTRを確認し、必要に応じてリライトする

## 3. 「1キーワード = 1記事」にしない

禁止:

- 表記違いだけで別記事を作る
- 同じ結論になるキーワードごとに記事を量産する
- 地名・人数・商品名だけを差し替えた薄い記事を増やす
- 検索ボリュームだけを理由にサイトテーマと合わない記事を作る

例:

- 「防災リュック 重すぎる」
- 「防災リュック 何キロ」
- 「防災リュック いらないもの」

これらが同じ「重量を減らす・中身を見直す」という検索意図であれば、1記事または既存記事の1章へ統合する。

## 4. 記事候補の評価軸

候補は最低でも次の軸で評価する。

| 評価軸 | 確認内容 |
|---|---|
| 検索需要 | 実際に検索される疑問・関連語か |
| サイト適合度 | 防災くらしガイドの読者課題に合うか |
| 既存記事との差 | 既存記事・Q&Aと検索意図が重複しないか |
| 読者価値 | 読後に具体的な判断・行動につながるか |
| 安全性 | 誤解時のリスクが高い場合、十分な一次情報を用意できるか |
| 内部リンク | 既存pillar/detail/productと自然につながるか |
| 収益接続 | 商品紹介へ自然につながるか。ただし収益性だけで決めない |
| 季節性 | 梅雨・台風・防災の日・冬季停電等の需要時期があるか |

検索ボリュームが小さくても、困りごとが具体的でサイトとの適合度が高いロングテールは候補に残す。

## 5. 優先する検索意図

一般的な大語だけでなく、具体的な疑問型・問題解決型を優先して調査する。

例:

- 携帯トイレ 何個必要
- 防災リュック 重すぎる
- 非常食 何日分
- 非常食 賞味期限切れ
- 台風 窓 テープ 意味ない
- 車 水没 エンジン かけていい
- 台風 車 どこに移動
- 停電 冷蔵庫 何時間
- マンション 断水 トイレ
- ポータブル電源 いらない
- 地震 車両保険

これらはあくまで調査起点の例であり、実際の記事化は既存記事との重複・根拠・安全性を確認して判断する。

## 6. 4つの振り分け

### A. 既存記事を強化

既存記事と検索意図がほぼ同じ場合。

例:
「ポータブル電源 防災 いらない」
→ B028「ポータブル電源は防災に必要？」へ「不要な家庭・必要性が高い家庭」を追加する方が自然なら、新規記事を作らない。

### B. 新規記事を作成

既存記事とは独立した検索意図・結論・行動があり、十分な内容量を持てる場合。

### C. Q&Aへ追加

短い疑問に明確な回答があり、詳細は既存記事へ送れる場合。

### D. 商品記事・商品導線へ反映

選び方・容量・数量・用途の比較が購入判断へ自然につながる場合。

## 7. ラッコキーワード等とSearch Consoleの役割分担

### キーワード調査ツール

用途:
- これから狙う需要の発見
- 読者の表現・疑問の把握
- ロングテール候補の発見
- 新規記事・Q&A候補の抽出

### Google Search Console

用途:
- 実際にサイトが表示されたクエリの確認
- 表示回数が多いがCTRが低いページの発見
- 順位8〜20位程度の強化候補発見
- 想定外クエリから既存記事の不足を把握
- 新規記事化すべき検索意図の検証

公開直後でデータが少ない期間は、Search Consoleだけに依存しない。

## 8. 季節性

防災テーマは需要の波が大きいため、検索需要のピーク直前ではなく1〜2か月前を目安に調査・公開・リライトを検討する。

例:

- 梅雨・大雨 → 春〜初夏に確認
- 台風 → 夏前〜台風シーズン前
- 防災の日 → 7〜8月
- 冬の停電・雪 → 秋
- 地震 → 通年。大きな地震直後の便乗量産はしない

## 9. 記録

キーワード調査から記事候補を採用する場合は、少なくとも次を記録する。

- 調査日
- 基点キーワード
- 使用した調査手段
- 検索意図クラスタ
- 既存記事との重複確認
- 振り分け結果
- 新規記事の場合の親pillar
- 優先度
- 季節性
- 採用・見送り理由

専用台帳を作成する場合も、正式な公開状態は `data/content_registry.json` を正とする。

## 10. 記事作成へ進む条件

新規記事へ進めるのは、次を説明できる場合。

- 誰が何に困って検索する記事か
- 既存記事ではなぜ十分に答えられないか
- この記事の結論・行動が何か
- どのpillar/detail/product/Q&Aと接続するか
- 必要な一次情報を確保できるか

説明できない場合は、新規記事化せず既存記事への統合を優先する。
